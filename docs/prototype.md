# Prototype implementation notes

This build implements the playable vertical slice in milestones 1–3 of the design document, plus a small codex, starter decks, deterministic practice opponent, browser save and replay laboratory. It is a demonstrator rather than a production multiplayer service.

## Rules decisions

The accepted defaults from design §15 are used: default exhausted entry; controller end-turn readying; draw two/keep one; batch attackers and blockers; no spillover; defender-selected output for a dual-output combat death; Consume pays a sacrifice before the occupied-slot check; neutral only pays generic costs; no stack, universal sacrifice or base energy. The 2026-10-11 user amendments replace discard recycling with immediate empty-library defeat and add simultaneous blocker retaliation with at most one blocker per attacker. Multi-blocking and reordering were tried, then removed by the latest amendment.

- Healing has no cap: the source specifies starting life and the loss condition, but no maximum life. Tests cover healing above ten.
- Opening the app uses a turn-five skirmish reached through ordinary bot commands. Fresh matches still start with ten life, five hand cards, five empty slots and the first draw skipped. No free starting energy or illegally pre-summoned board is granted.
- End-turn sequence is end-phase hooks, turn-end hooks, global damage clear, controller readying, pools clear, pass, turn-start hooks, draw choice. There are no temporary status/counter cards in this content set yet.
- Ties for hook processing use active-controller order, board slot, instance ID, then ability ID. ASCII comparison and seeded xorshift32 shuffling avoid locale/time/random dependencies. Resolution is limited to 256 internal orders per command; a breach rejects the entire transaction.
- If the assigned blocker disappears during attack/block triggers, that declared attack remains blocked and has no automatic spillover. This narrow extension edge-case default is explicitly recorded here; current starter cards do not exercise it.
- Incoming Consume monsters enter after the sacrifice is paid. Cost and target legality are established before any costs mutate state. Triggers run in the same bounded transaction. A post-cost target that leaves play is a no-op rather than being retargeted; this is deterministic and does not refund costs.
- Play targets, slots, Consume choices and payment allocations are supplied with the play command. Draw selection and dual death outputs use persisted discriminated choices; their continuations are data, not closures.
- The default UI payment allocation reserves faction requirements, then spends neutral and fixed-order faction colors for generic costs. Explicit allocations are available through the command API and covered by tests; a manual payment-picker UI is deferred.

## Runtime and content

`apply` validates command shape, version, revision, actor, phase, ownership, slots, targets, payment and choices, then resolves against an isolated clone. Rejections return the original state, with no RNG/event changes. State and commands are JSON-compatible. Life-based outcome is checked after the effect queue finishes, so a spell that kills both players yields a draw. Empty-library defeat stops resolution immediately, clears pending choices and takes precedence over later queued effects.

Abilities are registered once; cards reference their IDs and parameters. Implemented reusable abilities include Ready, Consume, Armor, Battlecry, Deathbound, Collector, a live attack aura and a self-damage trigger. Spell operations include damage, heal, draw, return and simultaneous damage to both players. Before hooks are currently used for play costs/Consume, entry readiness, damage and energy output. More lifecycle/replacement hooks can be added when a card requires them.

Static modifiers are calculated from live sources rather than modifying printed stats. Destroyed-source snapshots retain their controller, slot and bindings for death triggers. An extension cannot mutate through the public command interface; its normal API issues typed internal operations or returns constrained before payloads.

Valibot validates content, extension parameters and public command shapes. Deck limits use stable name/variant keys; Legendary is singleton. A deterministic bundle fingerprint includes canonical card data and registered extension versions. Extension code changes must bump their extension version; rules changes must bump the engine version. This prototype does not store historical content bundles or perform migrations.

The renderer consumes per-player projections. Opponent hand and deck identities and private draw events are omitted. Legal actions are filtered to the decision-maker. Hotseat uses an opaque handoff curtain when control changes, including blocking and death windows. The browser necessarily owns both sides of a local game; its full replay is not a public spectator export.

The R3F renderer decorates immediately committed state. Its bounded visual-event queue never decides legality or delays command execution, and reduced motion cancels it. Canvas failure switches to an HTML battlefield. Card inspection, hand and choice controls remain HTML.

## Demonstrator boundaries

- The opponent is a deterministic heuristic, not a strong balance AI. Starter decks and cards are fixtures for testing rules, not a balanced competitive set. Five scripted seeds finish legal matches; that is not a proof that every legal game terminates.
- Temporary SVG art covers all 21 cards and can be replaced through content. Living video illustrations, cinematic effects and production sound are deferred.
- There is no collection backend, arbitrary deck builder, content-authoring editor, lobby, online authority, matchmaking, transport idempotency, authentication or server persistence.
- Revision checking is present. A future server must authenticate actors, serialize match execution, deduplicate action IDs and filter all responses itself. The local renderer projection is not a substitute for that authority boundary.
- Replays are command-based and pinned to this engine/content bundle. The laboratory reconstructs state from the initial snapshot and the selected prefix of commands. It does not provide online recovery or historical bundle storage.
- Card images and fonts are local. The production output can be served as static files. Three.js remains the largest part of the presentation bundle.

Drawing the last card counts, whether from a normal turn draw, a spell, Deathbound or Collector. Discards never recycle. Terminal turn draws move any temporary choice cards to their owners' hands, remove the pending choice, emit one result and stop subsequent effects/attacks. The outcome reason is serialized and included in player/spectator projections and replay. Existing life-based simultaneous lethal remains a draw after the complete effect queue. Incompatible earlier sessions restart; this demonstrator does not migrate historical rules.

The opponent avoids self-defeating draw spells and accounts for Deathbound/Collector draws while selecting blocks, including the order in which collectors die. Library counts are visible beside life, with a warmer warning color near depletion. The result screen identifies an empty-library loss.

Readiness, exhaustion and undo remain separate corner indicators. ### Simultaneous retaliation and ordered multi-blocking (superseded by single blocking below)

User amendment, 2026-10-11, rules version `varhir-rules-0.4`: exhausted or ready defenders deal their Attack back to the creature they block. Several defenders may share an attacker; each defender may block only once. The attacker's single damage budget follows blocker assignment order, reserving enough raw damage to kill each earlier blocker after armor and existing marked damage, then sending the remainder onward. Excess never reaches the player. Every surviving assigned blocker strikes even if the exchange will kill it. All hits in an engagement happen before death checks or queued trigger effects; engagements still resolve in attacker board-slot order. If assigned blockers all leave before damage, the attack remains blocked. Attacker deaths run normal abilities but do not generate defensive death energy.

The client preserves other blockers when adding, moving or withdrawing one. Shared blocks show `#1`, `#2`, … beside the matching attack number; withdrawing and reassigning a blocker places it last. The attacking badge shows the shared blocker count. Each pair has its own persistent arrow, drawn outside card badges. The forecast counts unique blocked attackers and reports defending and attacking creature losses. The existing attacker confirmation remains mandatory.

The opponent searches blocker subsets and their assignment permutations, using the engine's shared damage planner for armor, marked damage and retaliation. It values killed attackers as well as surviving defenders and energy-color coverage. This remains a heuristic: it does not fully simulate changing auras and triggered effects across all candidate engagements. Damage allocation previews replacement hooks without issuing their effects; current armor is monotonic. Future non-monotonic damage replacements need an explicit allocation policy rather than the current lethal-damage binary search.

### One blocker per attacker, with retaliation

Latest user amendment, 2026-10-11, rules version `varhir-rules-0.5`: each attacker may have at most one blocker, and each defender may block at most one attacker. This supersedes the multi-block experiment above. Both creatures deal their full Attack simultaneously, with armor and marked damage respected, before deaths and queued effects resolve. Exhausted creatures still block and retaliate. Player spillover, death-energy eligibility and the mandatory attacker review stay unchanged. The engine rejects duplicate attackers or blockers in a formation transactionally.

Choosing a new defender for an occupied attacker replaces the previous defender. Moving a defender to another attacker frees its previous pair; unrelated pairs remain intact. Clicking an assigned blocker withdraws it. Both attacker-first and defender-first selection use the same assignment helper. Damage-order numbers and shared-block counts are removed from badges and help text. Each pair retains its cyan arrow and matching attack/block number. The opponent now searches one-to-one trades without subset or permutation ordering, valuing retaliation and armor alongside life, creature value, color coverage and library-depletion risk.

## Permanent positions (2026-10-11)

Rules version `varhir-rules-0.8` names each player's slots Left Flank, Left Wing, Center, Right Wing, Right Flank. Cards choose an empty slot on deployment and cannot move while on the battlefield. Adjacency means a difference of exactly one slot on the same friendly row, with no wraparound or gap compression. Three registered content extensions demonstrate adjacent Attack bonuses, immunity to flank blockers, and an automatic on-play Charge against a named enemy creature position. Charge does nothing to empty positions or bastions and uses normal damage resolution and Armor.

Block legality is projected as attacker/blocker pairs and enforced transactionally when blockers are submitted. The UI filters inline choices and battlefield highlights to these pairs; the bot uses them too and evaluates every legal deployment position. Authoring syntax and extension hooks are documented in `assets/README.md`. Existing card definitions remain unchanged.

## Lane attacks and automatic blocks (2026-10-12)

Rules version `varhir-rules-0.9`. The attack command now carries `lanes` (defaulting each attacker to its own position). An attacker may target its own lane or an adjacent lane, never two attackers on one lane. The enemy card in the targeted lane blocks automatically when `canBlock` allows it; otherwise the attack is unblocked and hits the player. The `block` command, the `block` combat stage and `LegalActions.blockers/blockPairs` were removed; `LegalActions.lanes` and `Combat.lanes` replace them. The defender no longer makes a decision in the declare/review stages (the attacker confirms in review, as before). Flank Evasion keeps its wording: flank cards cannot block it, so a flank lane is open against it.

The bot now chooses attackers and lanes by scoring each reachable lane (unblocked damage, or the trade against the lane's blocker) and takes lethal through an open lane. Its old blocker-assignment search was removed together with the regression tests for it (Deathbound/Collector library protection while blocking). The combat forecast accepts an in-progress attack draft so the UI previews lane choices before they are committed. Combat arrows now point at the targeted lane: cyan when a defender blocks there, gold when the lane is open.

Validation: unit tests for lane validation, automatic blocking, flank evasion by lane, forecast drafts, bot lane choices and creature action options; production build, no-DOM engine check, exact-replay simulations and the bot audit pass. 
### Dragging attackers onto lanes

During the declare stage, a ready creature can be dragged onto any highlighted enemy-row lane (its own or an adjacent one that no other attacker holds). Legal lanes are labelled "Attack" (a defender will block) or "Open lane" (the hit reaches the player), the arrow and its blocker preview follow the cursor, and dropping commits the lane. Dragging an attacker already selected re-targets it; an illegal drop returns it with a message. Clicking a creature still opens the lane menu, so the gesture is optional (and keyboard users keep that path). `resolveLaneDrop` in `cardInteraction.ts` holds the rule and reads the engine's `legal.lanes`; both the WebGL and flat boards forward pointer-down through `onDragStart`.

Browser check (Chromium, WebGL board, built site, saved turn-5 match): dragging five-slot attackers highlighted exactly the engine's lanes, drops created arrows and "Blocks N" labels, a two-lanes-away drop was rejected, and Attack advanced to review. The flat fallback board and touch input were not exercised.

## Guard (2026-10-12)

`guard` is a keyword on Mercenary Outriders. Attacks aimed at a lane **adjacent** to a Guard are blocked by the Guard instead of the lane's own card, even when that lane is empty. Resolution order in `laneBlocks`:

1. A Guard standing in a targeted lane blocks there first.
2. Remaining attackers are met left to right by a still-free adjacent Guard, otherwise by the card in their lane.
3. A card blocks at most one attacker, so one Guard cannot cover two lanes in the same combat.

`canBlock` restrictions still apply (a flank Guard cannot intercept a Flank Evasion attacker). The extension hook is `AbilityExtension.intercepts`; the bot and UI forecast both use `blockerFor`/`laneBlocks`. Combat arrows end on the card that actually blocks.

## Opening-hand mulligan (2026-10-12, rules `varhir-rules-0.10`)

`createMatch(..., { mulligan: true })` (used by the app, `simulate` and `audit:bot`) starts with a pending `mulligan` choice: player one first, then player two. The `mulligan` command takes up to `MULLIGAN_MAX` (2) distinct hand cards. The replacements are drawn first, then the returned cards are shuffled into the library, so a returned card cannot come straight back. Replacement draws are private events. An empty list keeps the hand. The bot returns up to two cards costing 4 or more, as long as the hand also holds a cheap play. Tests that build a match directly leave `mulligan` off.

## Battle log

Event text now names the blocked attacker and the source of damage.

## Spell animations

`SpellCast.tsx` is presentation only. When a `spell.cast` event arrives (yours or the bot's) it reveals the card with a caption, sends an orb from the reveal to the target (a card slot or the player's pool) and ends with an impact burst. ## Draw choice destination and discard pile (2026-10-12, rules `varhir-rules-0.11`)

After drawing two, the player keeps one and chooses where the other goes: the discard pile (default) or the bottom of the library. `choose` takes `other: 'discard' | 'bottom'`; the public `card.bottomed` event never names the card. Putting a card under the library halves the library clock (net -1 card per turn instead of -2), so it also tunes game length; the bot tucks a card under when it still rates it highly. The discard pile now has its own counter with a top-card thumbnail beside each player's library, and a "Discard piles" panel lists both piles, newest first. The saved-match fixture was moved to 0.11 after confirming it replays identically.

2026-10-14 · Rules `varhir-rules-0.17`: general response steps (formerly "death windows"; the resource formerly called death energy is now response energy). Whenever a creature with a printed energy output dies, on any turn and from any cause (combat, spells, sacrifices, the owner's own effects), its owner receives that energy as response energy and a response step in which only response-timed (internal timing `death`) spells can be paid with it. After combat the attacker's window opens first, then the defender's. Deaths caused by one action are batched into one window per player. A creature that dies inside an open window adds its output to that owner's pool (and to the other player's queued window); windows never loop. Dual-output creatures prompt a choice. The engine always opens both windows so skipping cannot reveal whether a player holds a death spell. ## One match path for local and online play (rules 0.20)

A match on this machine no longer has its own engine glue. `MatchAuthority` (the online host's authority) holds the state and command log for every match. `LoopbackRoom` wraps it for local play: the person plays one seat through `act`, and the opponent (the bot, or the scripted tutorial opponent) is a second seat that reads the authority's state and submits commands through the same `act` call a remote client uses. Hot seat is the same room with no opponent and the screen switching seats. `RtcRoom` is the network version of the same room contract.

`LiveMatchSession` is the only live session class: it consumes any `MatchRoom` and keeps per-seat snapshots as history. `MatchApp` renders what it is given; it no longer calls `apply` or replays commands. The bot pause before phase changes lives in the room (`bot.gate` / `advanceOpponent`), and the room holds the opponent while the screen presents the last move (`setHold`). Attack forecasts for a drafted attack are asked of the authority (`forecast`, also a `preview` message on the wire) instead of being computed in the client.

Saved matches were dropped: a started match lives only in the open tab. `tests/loopback.test.ts` plays a seeded match through the room and through the bare engine and compares the results; the tutorial is also played end to end through the room.
